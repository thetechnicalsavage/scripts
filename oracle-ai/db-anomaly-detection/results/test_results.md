## 6. What the numbers carry (stated, not adjusted)

- **A rival beats MSET-SPRT on the test day.** Static thresholds (R1) ranks first among the rivals by PLAN 7a's order and ranks above MSET-SPRT on the same order (13 vs 12 caught, 0 vs 3 false alarms). With one discordant incident (b = 0, c = 1) the test cannot tell the two apart on catches. No rival is significantly better or worse than MSET-SPRT on catches except the seasonal baseline, which is significantly worse (p = 0.0005).
- **MSET-SPRT's false alarms rose from 1 on the dev day to 3 on the test day**, above the 2 per 24 h the tuning rule allowed on dev. The rule is applied on dev only, so the chosen setting stands. The test-day episodes open at 10:19:31 (LOGONS,SQL_RT), 14:21:30 (LOGONS,SQL_RT), 21:19:30 (LOGONS); LOGONS is the first signal named in each. Their cause is not established here.
- **Slow drift was not caught the way the thesis expects.** No expected signal crossed its static threshold during run 126 (closest: APP_P95_MS at 0.998x for one minute, 0 minutes at or above). The static detector still counts as catching it at 5.5 min, through an episode that fired on W_USERIO, which is not in slow_drift's expected set (ATTR_P 0); it opened 2 more W_USERIO episode(s) inside the run, at 17:18:30, 18:18:30. MSET-SPRT caught it at 57.5 min and stayed flagged to the end, but its opening minute named REDO,BLKCHG first (ATTR_P 0). The catching rule counts both as caught; the post has to say how.
- **EM anomaly (D3) attributes nothing:** ATTR_P 0.000 over its 11 catches; for 8 of them the opening minute has no stored detail signal at all.
- **MSET-SPRT's ties:** median tie size at the cut 9.5 signals, so its lenient rate (9/12) is far above its ATTR_P mean (0.441). The rivals' median ties are 1-2 signals.
- **Seasonal baseline (R2) at k = 3** (EVAL_DEV: 1 episode(s), the first opening 00:29:30, status OPEN at the end of the day; EVAL_TEST: 1 episode(s), the first opening 00:29:30, status OPEN at the end of the day) catches nothing, because a catch needs an episode to start inside an incident, and it counts 1 false alarm a day, as results/dev_tuning.md section 6.1 expected.
- **Time to detect comes in whole-minute steps** (0.48, 0.50, 1.47, 1.48 ... min): the test-day incidents start at second 00-02 of a minute and the metric intervals begin at second 29-31, so every median sits at 1.48-1.51 min (the second interval of the incident). Medians therefore barely separate the detectors; the p90s do.
- **Write time.** The live scorer wrote an interval's row 1.65 min after it began (median over 59 in-database catches; 1.62-3.66). Every lag over 1.7 min belongs to run(s) 121 blocking_chain HIGH, whose minutes had null application signals; the live scorer waits up to 5 min for an incomplete minute. For the chosen variants that never ran live, the write time is the live FINAL model of the same detector scoring that interval in the same job run.
- **MSET-SPRT (D1), EVAL_DEV: an episode opened on the interval that contains the start of run 81 hard_parse_storm HIGH** (01:03:30 vs 01:04:02). grade() times an episode from its interval's begin, so it counts as a false alarm and the run as missed (no new episode starts in its window). Applied as written.
- **EM anomaly (D3), EVAL_TEST: an episode opened on the interval that contains the start of run 121 blocking_chain HIGH** (09:01:31 vs 09:02:01). grade() times an episode from its interval's begin, so it counts as a false alarm and the run as missed (no new episode starts in its window). Applied as written.
