# The frozen protocol

Section 7 of the lab's plan, published on its own so that `code/tools/freeze_check.py --verify` can check it.
It was written and frozen by sha256 on 10 October 2026, before any measured run, and was not changed after.
The rest of the plan is not published; references to its other sections point there.

## 7. Pre-registered comparisons (fixed in this version; any change needs a new plan version before the first measured run of that comparison)

### 7.0 Freeze, independence and what counts

- **Freeze.** Before the first measured run of steps 4, 5 or 7: the generators, the data files (`data/frozen/*.jsonl`,
  the images), the gold labels, C2's slot definitions, key terms and end-of-thread statuses, the matcher, the metric and
  statistics code (`py/lib/matcher.py`, `py/lib/stats.py`) and this section are frozen. (v0.3) The freeze is made on
  day 0 and recorded as the sha256 of every frozen file in a STATUS.md line and in `data/frozen/FREEZE.sha256`; this
  section is hashed as the text from the line starting `## 7.` up to (not including) the line starting `## 8.`. The
  ai_demos commit (`labs/agent-memory/`) comes later, after the leak scan (5.6), and must carry the same checksums;
  its commit id then goes into STATUS.md. `run_all.sh` refuses S4, S5 and S7 if any checksum differs: it runs
  `tools/freeze_check.py --verify --manifest-sha256 <the sha256 of FREEZE.sha256 recorded in STATUS.md>`, which
  re-hashes every frozen file and this section and first checks the manifest's own sha256.
- **Labels by construction.** Gold answers come from the generator's own structured records (the record a memory was
  written from, the slot an event was planted in), never picked by hand after seeing a search.
- **Blind review.** Before the freeze, with no result in existence, Codex (a different model) reviews the labelled sets
  against a checklist: each gold unique and correct, class B overlap rule, near-collision pairs, ambiguous slots and key
  terms, distractors that are really unlinkable, and (v0.2) every planted C2 fact stated in full inside one exchange
  (7.2). Flagged items are fixed before the freeze, never after.
- **Reviewer pass and the limitation (D11, changed by the operator on 10-Oct: "u can generate demo queries").** No
  human spot check. Before the freeze, with no result in existence, and after the blind Codex review: a reviewer pass
  over a seeded sample, 16 of the 160 C1/C3 queries (stratified: 4 per C1 class and 4 of C3) and 2 of the 12 C2
  threads, drawn with `random.Random(20261010)`. For each sampled item the reviewer re-derives the label from the
  generator's structured records and from the text, with its own script and without reading the gold field first, and
  compares. Every disagreement is either fixed in the generator, with the whole set regenerated, or recorded with the
  reason the label stands. A second model and a reviewer pass are not independent human reviewers, so the post states:
  "the queries, threads and their labels were generated by our scripts, checked blind by a second model (Codex) and
  by a seeded reviewer pass, and not checked by an independent human"; it makes no claim of independent labels.
- **No judgement after results.** An unmatched or ambiguous item is scored by the frozen rule, not by a person.
- **Interleaving.** Arm order is rotated per run to spread time-of-day effects.
- **Confirmatory and exploratory.** Only the tests named "confirmatory" below can support the word "better" in the post.
  Every other number is labelled exploratory or descriptive.
- **Technical abort, never a result-based one.** A run is void only if more than 5% of its LLM calls fail after the
  retries in 10.5, a database error stops the script, or a sanity check in 7.2 fails. A void run is repeated once; both
  are reported. No completed run is dropped.

### 7.1 C1 retrieval: HYBRID against VECTOR against KEYWORD (step 4)

- **Stores.** `RV_VEC` (VECTOR), `RV_HYB` (HYBRID, `search_index_sync=ON_COMMIT`), `RV_KEY` (KEYWORD, no embedder,
  `search_index_sync=ON_COMMIT`, written out although it is the default, so every inserted memory is searchable before
  the first query; `core/_db/hybrid.pyc:90`).
  VECTOR and HYBRID use `OracleDBEmbedder(connection=pool, model='ASKORACLE.ALL_MINILM_L12_V2',
  embedding_dimension=384, max_input_tokens=256)`. The same 400 memories go to each with
  `add_memory(..., autonomous_linking=False)` from a client with extraction off, so C1 makes no LLM call and is
  deterministic.
- **Queries (120, labelled at generation).** Class A, 40 identifier-only queries (`TKT-48213`); class B, 40 paraphrase
  questions with no identifier that share at most one content word with their gold memory (the overlap of every query
  is computed and published); class C, 40 natural-language questions that contain an identifier ("why was TKT-48213
  refunded?"). One gold memory per query. 15 class A and 15 class C queries target an identifier that has a
  near-collision sibling.
- **Call.** `search(query, user_id='BIZ_0001', max_results=10, num_hops=0, include_invalid_results=False)`, the default
  top-K configuration, no reranker, no pruning.
- **Measures.** Hit@1 (confirmatory); Hit@5, MRR@10, zero-result count, latency median and p90 (exploratory). A query
  with no result is a miss.
- **Confirmatory family (9 tests).** For each class A, B and C: HYBRID vs VECTOR, HYBRID vs KEYWORD, VECTOR vs KEYWORD,
  each an exact two-sided McNemar test on paired Hit@1 over that class's 40 queries; Holm-Bonferroni over all nine at a
  family-wise alpha of 0.05.
- **What counts as better.** X is better than Y on a class only if X has more Hit@1 there and the Holm-adjusted p is
  below 0.05. Otherwise the post says "no difference we could detect with 40 queries" and gives b, c and the adjusted p.
  With nine tests under Holm, the first rejection needs an exact p below 0.05/9 = 0.0056, which takes discordant pairs
  of at least 9 to 0, 12 to 1, 14 to 2 or 16 to 3 (v0.2; v0.1.3's "8 against 0", p = 0.0078, could never reject); the
  post says so, and a smaller lopsided split is reported as "not detectable with this design", not as a trend.
- **Wording rule.** "Exact identifiers" claims come from class A only; class C is "questions that contain an
  identifier". If VECTOR beats HYBRID anywhere, that is the headline of this section. The comparison is of the three
  strategies **as Agent Memory 26.8.0 implements them**, and the post says how each handles the same query text:
  KEYWORD wraps the whole query in one Oracle Text `{...}` escape (B9), HYBRID passes it unchanged as `search_text` to
  `DBMS_HYBRID_VECTOR.SEARCH` with `UNION` fusion and `topN` 10 (`core/_db/hybrid.pyc:200`, rendered offline in review),
  VECTOR embeds it with the same in-database model. It is not a verdict on Oracle Text or hybrid indexes in general.
- **Predictions from the code (reported as confirmed or refuted; not tests).** P1: KEYWORD returns no result for at least
  36 of the 40 class B queries. P2: KEYWORD returns no result for at least 30 of the 40 class C queries (B9: the whole
  question is one escaped phrase; stopwords inside it may let some match).
- **Precisions written with the generator (v0.3, before the freeze; `data/gen_retrieval_corpus.py`).** Memory ids
  `biz_m0001`-`biz_m0400` in event-time order; step 4 passes only `content`, `memory_type`, `timestamp`, `memory_id`
  and `user_id` (no metadata). Identifier formats: `TKT-nnnnn`, `PLN-XXX-nn`, `ADD-XXX-nn`, `DEV-nnnnn`, `INV-nnnnnn`,
  `NTE-nnnnn`; a near-collision pair is two identifiers at optimal-string-alignment distance 1 (truncation,
  transposition or one changed digit), and every other two identifiers are at distance 2 or more. The 120 gold memories
  are distinct and the classes do not share a gold. Class B overlap: content words are the lower-case alphanumeric
  tokens outside the generator's frozen stopword list (digits always count, other tokens need two characters), reduced
  by its light suffix stemmer, so "charged" and "charge" count as one shared word; each query's shared words are
  published with it; class B queries hold no identifier, month name or year. Hit@1 is the gold at rank 1 of the
  SDK's returned order; MRR@10 is the mean of 1/rank within the first 10 (0 when absent); latency median and p90 use
  numpy's `linear` percentile. A test with b = c is "no difference".

### 7.2 C2 automatic linking: POST_EXTRACTION against DURING_EXTRACTION against DISABLED (step 5)

- **Stores.** `AL_POST`, `AL_DUR`, `AL_OFF` (VECTOR, same embedder), recreated (`RECREATE`) for each run; before each
  recreation the store's MEMORY and MEMORY_LINK rows are exported to `results/s5/<mode>_r<n>.jsonl`.
- **Config.** `MemoryExtractionConfig(extraction_mode=MemoryExtractionMode.INLINE, memory_extraction_frequency=2,
  enable_context_summary=False, memory_link_extraction_mode=<mode>)`, LLM per 10.5 with `temperature=0`. Messages are
  added one exchange (two messages) at a time in the scripted order. INLINE, because the SDK default BACKGROUND may drop
  work when its queue is full (B26). `memory_extraction_window`, `memory_extraction_token_limit` and
  `memory_link_extraction_token_limit` stay at the SDK defaults (-1, 100,000, 100,000; `memoryextractionconfig.pyc`)
  and their resolved values are written to every run's transcript: the modes are compared as shipped.
- **Data rule that follows from the window (v0.2).** With the default window of -1 the extractor sees only the two
  newly added messages, so every planted fact, including both sides of each evolution event's new statement, is stated
  in full inside one exchange; anything that needs an earlier message to be understood would be lost by every mode
  alike and would only add noise. The generator enforces it and the blind review checks it (7.0).
- **Runs.** 3 per mode; order R1 POST, DUR, OFF; R2 DUR, OFF, POST; R3 OFF, POST, DUR.
- **Matching (frozen code).** Each gold fact slot has key terms. An extracted memory maps to a slot if its final stored
  text (which the resolver may rewrite, B15) contains all of the slot's key terms after case, whitespace, unit (`20GB` =
  `20 GB`) and date-format normalisation; a memory that maps to two or more slots is ambiguous and unmatched. A predicted
  link is correct if its source maps to the gold source slot, its target to the gold target slot and its
  `relation_type` equals the gold type (direction matters).
- **Confirmatory test (one), exactly as `py/lib/stats.py` will compute it.** Unit: the thread. For mode m and thread t,
  TP(m,t), FP(m,t) and FN(m,t) are summed over the 3 runs. Micro-F1(m) = 2·ΣTP / (2·ΣTP + ΣFP + ΣFN) over the 12
  threads, and 0 when the denominator is 0. Statistic T = micro-F1(POST) - micro-F1(DURING). For each of the 2^12 =
  4,096 assignments s in {0,1}^12 (the identity included), swap POST's and DURING's three counts in every thread with
  s_t = 1, recompute both micro-F1 values from the swapped sums and take T(s). Two-sided p = #{s : |T(s)| >= |T| -
  1e-12} / 4,096; ties count as extreme. Reject at p < 0.05 (the smallest attainable p is 2/4,096).
- **What counts as better.** POST or DURING "links more accurately" only if its micro-F1 is higher, the test rejects,
  **and** it made no harmful invalidation in any of its 3 runs (sum = 0). If the test rejects but the gate fails, the
  post reports both ("higher F1, but it invalidated N facts that were still current") and calls neither better; the same
  sentence is used whenever either automatic mode has a harmful invalidation, whatever the test says. Otherwise "no
  difference we could detect with 12 threads". DISABLED creates no links by design, so it is the cost
  baseline and the harmful-invalidation floor (0), not a contender; the post says that any automatic mode with a harmful
  invalidation did something DISABLED never does.
- **Descriptive, no test.** Per-run precision, recall and F1 for every run; type-agnostic pair recall; harmful
  invalidations (an automatic supersedes, refines or duplicates link whose target slot the gold marks current at the end
  of the thread: the notebook's trap); links on distractor pairs; slot coverage; LLM calls, input and output tokens
  (from `LlmGenerationCompletedEvent`, B18) and wall time per exchange. "Linking costs X" means POST or DURING minus
  DISABLED, as means with the range over runs.
- **Sanity checks (a failure voids the run, 7.0).** DISABLED creates no link; after each INLINE exchange the memory
  count is read back before the next one.
- **Size stated.** 36 gold links and 9 distractors per run: per-type cells are described, never ranked.
- **Precisions written with the matcher (v0.3, before the freeze; `py/lib/matcher.py`, `data/gen_conversations.py`).**
  A slot's end status is "replaced" exactly when it is the target of a gold supersedes, refines or duplicates link
  (the SDK invalidates those targets, B4), so a correct gold link is never a harmful invalidation; every other slot is
  "current". A key term is a short list of frozen variants (for example `4 lines` / `four lines`) and is present when any
  variant occurs on token boundaries (no letter or digit directly before or after), so `5 gb` is not found in `15 gb`.
  Normalisation: NFKC and case folding; dates with a day become "<month> <day>" with the year dropped (`2026-09-03`,
  `3 September 2026`, `03-Sep`, `Sep 3rd` all become `september 3`) and month abbreviations their full name; numeric
  dates with slashes are left as they are (day and month order is ambiguous); thousands separators and trailing decimal
  zeros removed; `20GB`, `20 gigabytes` become `20 gb` (also `mb`, `tb`, `gbps`, `mbps`, `dbm`); `80%` becomes
  `80 percent`; `QAR45`, `45 QAR`, `45 riyals` become `qar 45`; whitespace collapsed. A memory is matched only within its
  own thread (its `user_id`). Each gold link is credited at most once; a predicted link with an unmatched or ambiguous
  endpoint is a false positive. An invalidating link whose target matches no slot is not a harmful invalidation; such
  links are counted and reported apart (descriptive). A distractor link is any link, either direction and any type,
  between the two slots of a distractor pair; type-agnostic pair recall ignores type and direction. The generator
  checks, with the frozen matcher, that every slot's statement maps to exactly its own slot, that all of a slot's key
  terms are in its own exchange and no other exchange holds all of them, that each target comes in an earlier exchange
  than its source, and that a perfect run scores TP 36, FP 0, harmful 0. After the blind review (7.0) two more rules hold and
  are enforced: every refines source states a more specific version that implies its target (the SDK invalidates the
  target, so a lossy refinement would hide a fact; its link prompt asks for lossless lifecycle links, B15), and every
  dated statement names a complete month or a date before 1 July 2026, the first thread day, so no event is dated
  after the exchange that reports it.

### 7.3 C3 bounded context: top-K against LLM pruning (step 7)

- **Store and clients.** `RV_VEC` from step 4, read-only (REQUIRE_EXISTING). One client per arm, because the search
  configuration is set on the client and `pruner_llm` cannot be combined with `search_config` (B25).
- **Queries.** 40 questions whose gold set holds 2-5 memories by construction ("all roaming disputes in September 2025"
  is every memory generated with that topic and month).
- **Arms.** `TOPK10`: `TopKMemorySearchConfig(max_results=10)`, calls with `max_results=10`. `TOPK5`: the same with 5.
  `PRUNE_FAST`, `PRUNE_EXT`, `PRUNE_EXH`: `PruningMemorySearchConfig(pruner=<LLM>, evaluation_mode=FAST | EXTENDED |
  EXHAUSTIVE, protected_fraction=0.1)`, plus `num_probe_points=3` for EXTENDED only (it cannot be set for EXHAUSTIVE),
  calls with `max_results=10` (the candidate pool before pruning). Every call passes `token_budget=0` and
  `soft_token_budget=0`, which disable both budgets, so only top-K or the pruner decides what is returned (B25). The
  values 0.1 and 3 are the SDK's own defaults, written out so a later release cannot change them silently. Every
  call also passes `num_hops=0` (RV_VEC has no links, so this changes nothing but is stated). How the arms spend LLM
  calls (v0.2, from `core/_postsearch/_pruning.pyc` and `core/_pruners/_pruner.pyc:27`, one structured call per
  evaluated candidate): with 10 candidates, 1 is protected (ceil(10 x 0.1)); FAST probes up to 3 windows of 2 and stops
  early, so at most 6 calls; EXTENDED evaluates the windows starting at ranks 4, 7 and 9, so 6 calls; EXHAUSTIVE
  evaluates all 10. A query with fewer candidates evaluates fewer; EXTENDED may then log the SDK's "regions overlap"
  warning, which is counted, not suppressed.
- **Runs.** Pruning arms 3 runs; top-K arms 2 runs, which must return identical lists (determinism check), the first
  used.
- **Measures per query.** Returned estimated tokens: the sum over returned results of
  `max(1, round(len(result.formatted_content) / 3.5))`, which is exactly what the SDK's own budget code counts
  (`core/_postsearch/_tokenbudget.pyc:19-50` calling `apis/message.pyc:344`, B20), computed by us; gold recall and precision of the returned list; pruner calls and tokens;
  latency. Pruning arms: per-query values averaged over their 3 runs.
- **Confirmatory rule, exactly as `py/lib/stats.py` will compute it.** Resampling unit: the query. Each of 10,000
  resamples (numpy `default_rng(20261009)`) draws 40 query indices with replacement and, on that same draw for every
  arm, recomputes: token ratio R10 = Σ tokens(arm) / Σ tokens(`TOPK10`), recall difference D10 = mean recall(arm) - mean
  recall(`TOPK10`), token ratio R5 = Σ tokens(arm) / Σ tokens(`TOPK5`), and D5 = mean recall(arm) - mean
  recall(`TOPK5`). Bounds are one-sided percentile bounds. Alpha: 0.05 split equally over 3 arms x 2 decisions = 6
  decisions, so each bound is taken at 0.05 / 6 = 0.833% (the 99.167th percentile for an upper bound, the 0.833th for a
  lower bound). Within a decision every condition must hold (intersection-union, so no further split).
  (a) "smaller context without a material recall loss": upper bound of R10 < 0.80 **and** lower bound of D10 > -0.10.
  (b) "better than simply taking 5": lower bound of D5 > 0 **and** upper bound of R5 <= 1.00.
  Otherwise the post says pruning did not show a benefit on this set. Margins fixed now: a cut of less than 20% is not
  worth an extra LLM call per search; losing more than one relevant memory in ten is material; pruning that returns
  more than `TOPK5` while finding more is not "better than taking 5".
- **Wording rule.** These are returned-context and gold-recall measures; answer quality is not measured, and the pruner's
  own tokens are always shown beside the tokens it saves.
- **Precisions written with `py/lib/stats.py` (v0.3, before the freeze).** The one shared draw is
  `numpy.random.default_rng(20261009).integers(0, 40, size=(10000, 40))`; bounds use numpy's `linear` quantile at
  0.05/6 and 1 - 0.05/6. A resample whose `TOPK10` or `TOPK5` token sum is 0 gives a non-finite ratio, and a
  non-finite bound makes its condition false. Estimated tokens use Python's `round` (half to even), as the SDK does.
  Recall counts distinct returned ids; the precision of an empty list is 0.
